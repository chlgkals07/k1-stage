# 실물 검증 체크리스트 — 인수인계용

개소식(8/17) 이후 로봇을 안 켠 지 한 달이 지났다. 그동안 로봇과 라디오를
다른 사람이 만졌을 수 있으니, **이 저장소가 "참"이라고 적어둔 것과 로봇의 실제
상태가 같은지부터 확인**하고 시작한다. 코드를 믿지 말고 실측한다.

순서는 RC(라디오·전파 계층) → 로봇(소프트웨어·모드) → 최종(통합) 이다.
**안전 관련 항목(❌ 표시된 줄)은 실패하면 다음 단계로 넘어가지 않는다.**

## 사용법

- E-stop 담당자를 먼저 정한다. 혼자 하지 않는다.
- 항목마다 대괄호를 체크하고, `___` 자리에 실측값을 적는다.
- 다 채운 뒤 이 파일을 그대로 커밋해서 남긴다 (다음 사람이 또 처음부터 재현하지 않게).
- 안 되는 항목이 나오면 [RUNBOOK §5 장애 대응](RUNBOOK.md#5-장애-대응)부터 본다.

## 1. RC 검토 (라디오·전파 계층)

### 1.1 라디오 인식

- [ ] 위쪽 USB-C → PC 연결 → **Serial** 팝업 (아래쪽 포트는 충전 전용, 인식 안 됨)
- [ ] SYS → Hardware → USB-VCP = **LUA**
- [ ] SYS → Tools → **K1PC** 실행 → 화면 `K1PC vX.X IDLE`
- [ ] 버전: v___ (`group_stage/RUNBOOK.md` §0 표의 v2.2/v2.3와 비교 — v2.2면 정지가
      옛 방식(ReadyPose)으로 동작하니 v2.3 패치 권장)

### 1.2 다이얼 슬롯 매핑 대조 — "예전 rc list랑 달라졌다"의 핵심

RC 다이얼 슬롯 번호는 `solo_stage/motions.yaml`의 `slot:` 필드가 소프트웨어 쪽
진실이고, 로봇 실물 `k1_config.yaml`의 selector 테이블이 하드웨어 쪽 진실이다.
둘이 어긋나면 "버튼은 눌리는데 다른 동작이 나가거나 아예 안 나간다."

```bash
# 로봇 최신 k1_config.yaml 백업을 받은 뒤 — 이 명령은 읽기 전용이다.
python3 tools/verify_robot_rc_config.py <받은 k1_config.yaml>

# 위 검사가 통과한 뒤에만 rc_list를 재생성한다 (이 명령은 motions.yaml을 바꾼다).
python3 rc_link/gen_rc_list.py <받은 k1_config.yaml> solo_stage/motions.yaml
git diff solo_stage/motions.yaml   # rc_list 섹션에 diff 가 있는지만 본다
```

- [ ] diff 없음
- [ ] diff 있음 — 바뀐 슬롯 기록: ___________________________________
      (git diff 결과를 그대로 여기 붙여넣거나 별도 커밋으로 반영)
- [ ] `verify_robot_rc_config.py` 통과 — A/B 40슬롯 일치 + B-202 `MimicGuapVer2`
- [ ] 패드 12개 동작이 전부 다이얼에 있는지 (`test_rc_backend.py`의 `KNOWN_A`/`KNOWN_B`
      앵커, `RUNBOOK.md` "RC delta" 절 참고)

### 1.3 SD/SC/SB 스위치 상호작용 — 가장 헷갈리는 실패 모양

로봇은 **API 권한일 때 RC 펄스를 조용히 무시**하고, 라디오는 그래도 `OK`를 준다 —
PC 화면엔 성공으로 뜨는데 로봇은 안 움직이는 원인 1위. 지금 이 세션에서 고친
버그(dance 시작 전 게이트웨이 확인)도 이 계열이라, **직접 재현해서 실패 모양을
눈으로 봐 둔다.**

- [ ] SD를 OFF→ON(API 켬) 한 채로 RC로 손동작 1개 쏴본다 → **무시되는 게 정상**
- [ ] SD를 다시 OFF로 내리고 같은 동작을 쏜다 → **이번엔 실행되는 게 정상**

### 1.4 시리얼 왕복 (의심될 때만)

`rc_link`의 벤치 도구로 PC↔라디오 latency를 잰다 (기준: avg 0.4ms대).
