## 한 일: 운영자 정지(preempt) 경로

### 왜

`gateway.py`의 `submit()`이 `_current`가 있으면 무조건 거부해서, **한 번 시작된 모션을
멈출 방법이 없었다.** 유일한 탈출구는 RC Damping과 E-stop(물리)뿐이었다. 그건 최종
안전장치지 운영 중 "지금 이 동작만 멈춰"에 쓰는 수단이 아니다.

`motions.yaml`에는 `control_states`로 `ReadyPose`가 이미 있었고 주석에
*"LLM이 '그만', '쉬어' 같은 말에 쓸 수 있다"*고 적혀 있었지만, `gateway_config.yaml`
allowlist가 Mimic 3개뿐이라 필터에 걸려 도달 불가능했다. **정지 능력이 카탈로그에만
존재하고 실제로는 없던 상태다.**

### 설계 판단 세 가지

**1. 정지는 LLM에 열지 않는다.** 음성 정지는 발화 종료 → VAD → 전사 → LLM 추론 →
function call → fetch → relay → gateway → ROS로 1.5~3초가 걸린다. 정지는 결정론적이고
즉시여야 하므로 운영자 버튼(~50ms)만 열었다. `build_tools()`와 PERSONA는 손대지 않았고
`ReadyPose`는 여전히 LLM enum에 없다 (`test_stop_state_is_not_exposed_to_the_llm`).

**2. 정지 경로는 `request_available`을 검사하지 않는다.** 일반 `_ready_locked()`는 이
플래그를 요구하는데, **Mimic 실행 중 `api_request_available`가 true로 유지되는지 아직
모른다.** false라면 정지가 거부되어 기능 자체가 무의미해진다. 그래서 정지는
`authority == API`, `heartbeat_valid`, status 신선도만 검사하고 allowlist·busy·cooldown은
전부 우회한다. **이 가정이 이번 변경의 가장 큰 미검증 지점이다.**

**3. `interruptible`은 데이터만 넣고 강제하지 않는다.** 정지를 막는 조건을 만드는 건
안전에 역행한다. 이 필드는 향후 "실행 중 다른 모션으로 교체" 기능에 쓴다.

### cooldown

`MimicBadChestpopVer2`에만 8초. **기본값 0이다** — PERSONA와 STATUS 문서가 "새 발화에서
같은 동작 재실행"을 실물 검증된 행동으로 명시해뒀고 `test_lifecycle_and_single_request`가
그걸 검증한다. 인사류에 cooldown을 걸면 검증된 행동이 깨진다.
cooldown은 정지를 막지 않는다.

## 한 일 2: 응답 길이 · VAD · 모션 발사 시점

### 왜

말이 길고, 턴 전환이 어색하고, **말과 동작이 어긋났다.**

싱크 문제의 원인은 `static/index.html`이 `response.done`에서 모션을 쐈기 때문이다.
`response.done`은 응답의 **마지막** 이벤트다. 즉 K1이 말을 다 마친 뒤에야 요청이 나가고,
그 뒤로도 fetch → relay → gateway → ROS → 상태머신 → Mimic 전환이 남는다.
말이 끝난 다음에 팔이 움직였다.

### 발사 시점 분리

문서 확인 결과 `response.function_call_arguments.done`에는 `item_id`, `name`, `arguments`가
있지만 **`call_id`가 없다.** `call_id`는 `response.done`의 output item에만 확실히 있다.

이 사실이 설계를 갈라준다.

| 하는 일 | 시점 | 필요한 것 |
|---|---|---|
| 모션 발사 | `response.function_call_arguments.done` (이름/인자만 있으면 됨) | `name`, `arguments` |
| 모델에 결과 반환 | `response.done` (지금과 동일) | `call_id` |

대화 흐름은 그대로 두고 동작만 앞당겼다.

**중복 발사 방지**: `item_id`로 대조하지 **않는다.** id 표기가 어긋났을 때 잘못된 결과를
모델에 돌려주는 것보다 **동작이 두 번 나가는 쪽이 훨씬 나쁘다** — 첫 동작이 빨리 끝나면
gateway가 두 번째를 거부하지 못하고 실제로 두 번 실행될 수 있다. 대기 항목이 있으면
무조건 재사용한다. PERSONA가 한 발화당 tool call 1회로 제한하므로 대기 항목은 최대 하나다.

**미처리 rejection 차단**: 이른 발사의 promise는 한동안 아무도 await하지 않는다.
`dispatchMotion()`에서 삼키지 않으면 `response.done`에서 `function_call_output`을 못 보내
대화가 멈춘다.

### 길이와 턴 전환

- `session.max_output_tokens` = `REALTIME_MAX_TOKENS` (기본 200)
- `session.audio.input.turn_detection` — 지금까지 **아예 설정되지 않아 기본값으로 돌고 있었다.**
  `server_vad` 기본, `silence_duration_ms` 400. 전부 환경변수 (README 표 참조)
- `create_response` / `interrupt_response`를 명시 — 사람이 K1의 말에 끼어들 수 있어야 자연스럽다
- PERSONA에 문장 수 규칙 추가. 캡은 문장 중간에서 잘라내므로 일상적 길이 조절 수단이
  못 되고, 실제 길이는 프롬프트가 잡아야 한다

세션 설정을 `_mint_token()` 밖으로 `build_session()`으로 빼서 네트워크 없이 검증한다.

`test_ui_dispatch.py`(신규)는 `index.html`의 스크립트를 그대로 뽑아 DOM/fetch를 stub하고

### 왜

`server.py`에 고정 토큰 인자(`--gateway-token` / `--relay-token`)가 이미 있었는데
안 쓰고 있었을 뿐이라 **코드 변경은 없었다.**

### 무엇을 막는가

단순 자동화가 아니라 오늘 실제로 겪은 실패를 막는다.

- **ROS bringup 확인** → 없으면 "`go` 먼저 실행하라"며 멈춘다
- **PC↔로봇 md5 대조** → 배포 누락을 조기에 잡는다 (`relay_backend.py` 누락으로
  gateway가 시작조차 못 했던 그 유형)
- gateway가 이미 떠 있으면 재사용, relay 경로는 운영 경로(50.1) 우선

### 구현 중 잡은 버그 3개

셸 스크립트라 테스트가 얇아 직접 훑어서 찾았다.

1. **`head()` 함수가 `head` 명령을 가렸다.** `pc_lan_ip()`의 `| head -1`이 내 함수를
   호출해 IP 검출이 깨졌다. → `section()`으로 개명.
2. **`pgrep -x ai_sapiens_sim2real_node`는 절대 매칭되지 않는다.** 리눅스 `comm`이 15자로
   잘려 `ai_sapiens_sim2`가 되기 때문이다. ROS가 떠 있어도 "`go` 하라"고 오안내했을 것이다.
   → `pgrep -f '[a]i_sapiens_sim2real_node'` (대괄호로 감싸 셸 자신이 안 잡히게).
3. **`(( x++ ))`는 x가 0일 때 종료코드 1**이라 `set -e`와 함께 쓰면 위험하다.
   → `x=$((x + 1))`.

### 토큰 정책 변경

토큰을 **고정**으로 바꿨다. 대가로 **같은 네트워크에서 URL을 한 번 본 사람은 계속 접근할 수
있다.** 로드맵 §7의 "재시작 시 새 token" 항목과 STATUS 문서의 보안 경계를 함께 갱신했다.
비밀값은 `~/.k1/secrets.env`(chmod 600, 리포지토리 밖)에 둔다.
