## 0. 먼저 — "끊기면 ReadyPose로 간다"는 걱정은 사실이 아니었다

로봇 소스로 확인한 실제 실패 거동:

| 끊긴 것 | 로봇이 하는 일 | 근거 |
|---|---|---|
| PC↔로봇 Wi-Fi | **아무 일도 안 남.** 현재 상태 유지 | 서버가 죽어도 로봇 모드 전이는 teleop/서비스로만 일어남 |
| RC 링크 (라디오 꺼짐/전파 두절) | **Damping (힘 빠짐)** — 0.2초 만에 | `mode_controller.cpp` `failsafe_reason()` → `make_damping_state_request()`, `teleop_input.timeout: 0.2` |
| PC 프로세스 종료 / USB 분리 | 라디오가 0.5초 내 게이트 해제 → **물리 스위치 위치로 복귀** | `K1PC.lua` keepalive → `abortAll` → `releaseAll` |
| 동작이 정상 종료 | **Velocity(보행·균형)** 로 스스로 복귀 | `k1_config.yaml` `mimic_defaults.on_complete: Velocity` |

즉 **ReadyPose 로 가는 자동 경로는 없었다.** 유일하게 ReadyPose 를 보내던 것은
**사람이 누르는 빨간 정지 버튼**이었고 (`stop_state: ReadyPose`), 그건 고쳤다.

`ready_pose` 는 `kind: posture` — 균형 정책 없이 관절을 3초에 걸쳐 고정 자세로 끌어당긴다.
팔굽혀펴기·스쿼트처럼 바닥에 붙은 자세에서 이걸 누르면 가장 넘어지기 쉽다.
`velocity_policy` 는 `kind: policy` (locomotion) 로 균형을 잡고, 로봇이 동작 사이에
평소 머무는 상태다. **그래서 정지는 Velocity 로 보낸다.**

> 라디오 스틱(CH1/CH2/CH4)은 전부 자동 중립 복귀축이라, Velocity 로 가도 아무도
> 스틱을 안 잡고 있으면 제자리에서 균형만 잡는다. 스로틀(CH3)은 속도에 매핑돼 있지 않다.

## 1-b. 잠금 타이밍 구조 (최종)

기준은 **sim 클립 길이 = 그 동작이 도는 시간**이다. 세 시계가 같은 기준에서 나온다.

| 시각 | 일어나는 일 | 주체 | 식 |
|---|---|---|---|
| 0.0s | 명령 발사 | 패드/운영자 | — |
| +L | 로봇 동작 종료(추정) | 로봇 | L = 클립 길이 |
| **+L+2.0s** | 패드 진행바 종료 → 패드 잠금 해제 + `/stage idle` | 패드 | 기존 값(안 건드림) |
| **+L+2.0s** | RC 로봇 busy 해제 | 서버(RC) | 패드와 **같은 시각**으로 맞춤 |
| **+L+3.0s** | 서버가 화면을 idle 로 되돌림 (패드가 이미 보냈으면 무시) | 서버 | 안전망 |

- **패드가 주 해제자, 서버가 1초 뒤 안전망**이다. 패드가 죽었거나 운영자가 직접
  실행했으면 서버 것만 걸려 `+L+3.0s` 에 풀린다.
- 여백 2초를 남긴 이유: 실기가 sim 보다 조금 느릴 수 있고, 여백이 0이면 로봇이
  마무리 동작 중일 때 다음 명령이 나간다.
- 실측 예: 손인사 3.98s → 5.98s 해제 / 배꼽인사 4.98 → 6.98 / 스쿼트 3.98 → 5.98 /
  구압v2 11.98 → 13.98 / 마카레나는 rc_list note 값 29.5s 를 그대로 쓴다.
- 클립이 없는 동작(운영자 목록의 나머지)은 화면 복귀 기본 12초, RC busy 기본 30초.
  둘 다 stage TTL(60초)이 최종 백스톱이다.
- **무대(dance)는 이 사다리를 쓰지 않는다.** 영상 종료 신호가 주 해제자이고,
  `max(영상 길이, 동작 추정) + 5초` 가 안전망이다 (응원단 89.5s).

너무 빠르면 관객이 로봇이 아직 움직이는데 다음 버튼을 누르고, 너무 늦으면 쇼가
늘어진다 — 여백 2초가 그 사이다. 현장에서 늘리거나 줄이려면 `pad.html` 의 `+2000`,
`server.py` 의 `EXEC_IDLE_MARGIN_SEC`, `rc_backend.py` 의 `BUSY_MARGIN_SEC` 세 값이
같은 뜻이므로 함께 움직이면 된다.

## 3. 남은 것 — 실기 전에 사람이 해야 하는 일

### ① 로봇 다이얼 교체 (필수, 안 하면 패드 12번이 RC 에서 계속 죽음)
로봇 `ai_sapiens` 의 `config/k1_config.yaml`:
```yaml
selectors:
  mimic_selector_b:
    table:
      202: MimicGuapVer2      # 기존 MimicGuap 에서 교체
```
표기는 둘 다 "구압/GUAP"라 화면상 차이는 없다. 바꾼 뒤 로봇 백업을 다시 떠서
`rc_link/gen_rc_list.py <k1_config> motions.yaml` 로 rc_list 를 재생성하면 정합이 유지된다.
(PC 쪽 `motions.yaml` rc_list 는 이미 v2 로 바꿔 뒀다.)

### ② 라디오 K1PC.lua 에 `VEL` 추가 (선택 — 안 해도 예전처럼 동작)
현재 RC 정지는 `VEL` 을 먼저 시도하고, 라디오가 `ERR` 을 주면 기존 `STOP`(ReadyPose)로
폴백한다. 즉 **SD 카드를 안 건드려도 지금과 똑같이 동작한다.** 옮기면 RC 경로도
locomotion 복귀가 된다. `radio/K1PC.lua` 의 `startPulse` 분기에 3줄:

```lua
  elseif kind == "VEL" then
    setGv(GV_CH6, -100)  -- CH6 1000
    setGv(GV_CH7, 100)   -- CH7 2000  → 둘이 합쳐 code 3 = Velocity
```
그리고 `handleLine` 의 `STOP/DAMP` 분기에 `VEL` 을 추가해
`startPulse("VEL", nil, nil, nil, T_GATE_LAG)` 를 부르고 `OK VEL` 로 답하게 한다.
(옮긴 뒤에는 도구 EXIT → 재실행 필요.)

### ③ RC 모드에서는 라디오 **SD(CH8, API arm)를 내려야** 명령이 먹는다
로봇은 API 권한일 때 **teleop 전이를 무시한다** (`mode_controller.cpp`
`resolve_authority_owned_state`: Api 면 서비스 요청만 소비). 로봇 쪽 gateway 가
떠 있고 SD 가 올라가 있으면 우리 RC 펄스는 **조용히 무시되고**, PC 는 라디오에서
`OK` 를 받았으므로 성공으로 보고한다 — 무대에서 가장 헷갈릴 실패 모양이다.
→ RC 모드 전환 절차에 "SD 내리기"를 넣을 것. (실기 P2 에서 확인)

### ④ 실기에서 확인할 것
- 정지 → `request_mode_by_name("Velocity")` 가 실제로 수락되는지 (Damping 상태에서 1회)
- RC 발사 관측(`발사 관측 OK`)이 실제로 뜨는지, 뱅크/슬롯이 의도대로 나가는지
- dance 오프셋 재보정: `-rc` 프리셋 3종은 지금 `offset_ms: 0` 이다. RC 경로 지연은
  Wi-Fi 대비 수십 ms 차이라, **`-api` 값(-1500 / +500 / 0)에서 출발**해 미세 조정하는 편이
  0 에서 시작하는 것보다 훨씬 가깝다.

## 4. 일부러 **안 고친** 것 (동작은 하지만 다듬을 여지)

지금 잘 돌아가는 경로를 건드리지 않으려고 남겨 뒀다. 나중에 판단할 것:

1. 무대 중 디스플레이를 새로고침하면 영상이 **0초부터** 다시 재생된다(로봇과 어긋남).
   합류 자체는 되므로 사고는 아니다. 고치려면 `media_at` 기준으로 `currentTime` 을 계산.
2. 디스플레이가 preview **도중에** 처음 열리면 클립 목록을 아직 못 받아 영상 대신
   동작 이름만 크게 뜬다. 다음 화면 전환 때 정상화된다.
3. 무대 오디오 잠금 오버레이("화면을 한 번 탭해 주세요")는 자동재생이 막힌 브라우저에서
   계속 남는다. 현장에서 TV 를 한 번 탭하는 절차로 커버 중.
4. `executing` 화면은 카탈로그 한글명을 쓴다 — 무대 3종을 **수동으로** 실행하면
   "체스트팝 v2" 가 뜬다. 무대(dance) 경로에는 안 뜬다(§1-9).
5. `/dance` 배지가 RC 모드에서 "MODE 확인 불가"로 뜬다(표시만).
6. `-api`/`-rc` 프리셋 6개가 한 목록에 섞여 있고 현재 경로와 자동으로 묶이지 않는다.
   운영자가 골라야 한다.
7. `run.sh` 에 RC 실행 경로가 없다. RC 는 운영자 화면 토글로만 켠다(설계대로).
8. RC 발사 관측이 **불일치**여도 실행은 성공으로 보고한다(경고만).
9. K1PC 의 `abortAll` 은 게이트를 내리면서 같은 틱에 GV 를 0으로 되돌린다. 게이트 반영
   지연(≤100ms) 동안 CH7=1500(ReadyPose) 이 전파될 여지가 이론상 있다. 정상 종료 경로는
   `T_GATE_LAG` 를 두는데 abort 경로만 없다. 실측으로 확인되지 않아 건드리지 않았다 —
   P2 에서 `/ai_sapiens_rc/status` 를 보며 케이블을 뽑아 확인하면 결론난다.
